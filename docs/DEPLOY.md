# Deploying Pubshift

The whole site is a directory of static files plus one 465 KB WebAssembly binary. There is
no application server, no database, no queue and no per-conversion cost, because the
conversion happens in the visitor's browser. That is not a hosting convenience — it is the
product argument in `docs/POSITIONING.md` made physical, and it has a consequence worth
stating plainly:

**this site can sit online for years, unattended, for the price of a domain name.**

Demand for a Publisher converter ends shortly after 1 October 2026. A deployment that needs
monthly attention is a liability against that timeline. Everything below is chosen to
survive being forgotten.

---

## 1. What you are deploying

```
apps/web/out/          the entire site, after `npm run build`
├── index.html         ~20 HTML files
├── _next/static/      hashed JS and CSS
├── wasm/<sha256>/     the extractor: index.mjs, dist/pubshift.mjs, dist/pubshift.wasm
├── licences/          MPL-2.0 text + third-party notices  (a licence obligation, not decoration)
└── _headers           security and caching rules for the CDN
```

Measured on the build in this repo: 8 routes, 103 KB of shared JS, and the 465 KB `.wasm`
which is fetched only when someone actually drops a file in.

---

## 2. Build it

### Prerequisite: the extractor must exist

`wasm/dist/` is gitignored, so a fresh checkout has no converter in it. The web build
**refuses to proceed** without one rather than shipping a converter-shaped site that cannot
convert:

```bash
node tools/licence/sources.mjs fetch    # pinned libmspub + librevenge into third_party/
./wasm/build.sh                         # needs emscripten on PATH
node wasm/test/parity.mjs               # the oracle: WASM must agree with the native build
```

`fetch` verifies each source against the commit hash and digest recorded in
`wasm/third-party.json`, and refuses to unpack anything that does not match. See §7.

### Build the site

```bash
cd apps/web
npm run build
```

`prebuild` runs two generators first, and neither is optional:

| Script | What it does | Why it cannot be skipped |
|---|---|---|
| `scripts/prepare-assets.mjs` | Copies the extractor into `public/wasm/<sha256-16>/` and the licence texts into `public/licences/`; writes `lib/wasm-asset.ts` | The content-addressed path is what makes immutable caching *true* rather than a lie, and the licence texts are an MPL obligation that has to travel with the binary |
| `scripts/emit-host-config.mjs` | Renders `public/_headers` and `vercel.json` from the header list in `next.config.mjs` | See §4 — the headers in `next.config.mjs` do nothing on a static export |

The result is `apps/web/out/`. That directory is the deploy.

## 3. Hosting

### Cloudflare Pages — the recommended one

Free tier, unmetered bandwidth, reads `_headers` straight out of the published directory,
so the generated header file is applied with no extra configuration and nothing to keep in
sync.

```bash
npx wrangler pages deploy apps/web/out --project-name pubshift
```

Or connect the repository and set:

- **Build command:** `npm install && npm run build -w @pubshift/web`
- **Output directory:** `apps/web/out`
- **Environment:** `NEXT_PUBLIC_SITE_URL=https://pubshift.app`

> The repository build needs `wasm/dist/pubshift.wasm`, which is gitignored and cannot be
> rebuilt on Cloudflare's runner (no emscripten). Either commit the built `.wasm` for
> deployment, or build locally and use `wrangler pages deploy`. **Uploading a prebuilt
> directory is the simpler and more reproducible choice**, and it keeps the emscripten
> toolchain off the critical path of a deploy you may be doing in a hurry.

### Netlify

Same `_headers` file, same output directory.

```toml
# netlify.toml
[build]
  command = "npm run build -w @pubshift/web"
  publish = "apps/web/out"
```

### Vercel

`vercel.json` is generated by `emit-host-config.mjs` and **must be committed**, because
Vercel reads it before the build runs. That makes it the one host where the headers can
drift from `next.config.mjs` if someone edits the CSP and forgets to rebuild. If you use
Vercel, add a CI check that `npm run prebuild` leaves `vercel.json` unchanged.

### Plain nginx, Caddy or S3+CloudFront

`_headers` means nothing to these; translate it by hand. The rules that matter:

```nginx
# nginx
types { application/wasm wasm; }          # older nginx does not know .wasm

location /wasm/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location /_next/static/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
    try_files $uri $uri/index.html =404;   # trailingSlash: true emits directories
    add_header Cache-Control "public, max-age=0, must-revalidate";
}
```

```caddyfile
# Caddy — already knows application/wasm
pubshift.app {
    root * /srv/pubshift/out
    file_server
    @immutable path /wasm/* /_next/static/*
    header @immutable Cache-Control "public, max-age=31536000, immutable"
    header /* {
        Content-Security-Policy "…copy from out/_headers…"
        X-Content-Type-Options nosniff
        Referrer-Policy strict-origin-when-cross-origin
        X-Frame-Options DENY
    }
}
```

## 4. Headers: the trap

**`headers()` in `next.config.mjs` does nothing under `output: 'export'`.** Next says so,
once, in a build warning that is easy to scroll past:

```
⚠ rewrites, redirects, and headers are not applied when exporting your application,
  detected (headers).
```

A static export is a directory of files. There is no Next server left to add a header, so
the carefully-written Content-Security-Policy is simply **absent in production** unless the
CDN is told about it separately. This is a good way to ship a site that looks locked down in
the repository and is wide open in reality.

`scripts/emit-host-config.mjs` closes that gap by importing `next.config.mjs`, calling
`headers()`, and rendering the real list into `public/_headers` and `vercel.json`. One
source of truth, two outputs, no drift. Change the CSP in `next.config.mjs` and rebuild;
never hand-edit `out/_headers`.

### Caching

| Path | Policy | Why |
|---|---|---|
| `/_next/static/*` | `max-age=31536000, immutable` | Next puts a content hash in every filename |
| `/wasm/*` | `max-age=31536000, immutable` | `prepare-assets.mjs` puts the binary's own SHA-256 in the directory name, so a rebuilt extractor is a *new URL* |
| `/licences/*` | `max-age=3600` | Fixed names; must be able to change |
| HTML | `max-age=0, must-revalidate` | It is what points at the hashed URLs; stale HTML makes everything else stale |

`immutable` on a fixed filename is a promise you cannot keep — it strands returning visitors
on an old binary for a year. The content-addressed directory is what earns the header.

### `.wasm` must be served as `application/wasm`

`WebAssembly.instantiateStreaming` rejects any other content type, and the failure is a
console error on a page whose only feature is the thing that failed. Cloudflare, Netlify and
Vercel get this right; nginx before 1.21.1 does not. The rule is stated explicitly in
`_headers` anyway, because it costs nothing and removes the whole class of problem.

### Cross-origin isolation is *not* required

Checked against the built module rather than assumed:

```
$ grep -c 'SharedArrayBuffer\|pthread' wasm/dist/pubshift.mjs   →  0
$ strings wasm/dist/pubshift.wasm | grep -ci 'pthread|shared'   →  0
```

The extractor is single-threaded and uses no `SharedArrayBuffer`, so **no
`Cross-Origin-Opener-Policy` or `Cross-Origin-Embedder-Policy` header is needed**, and
adding them would be cargo cult. `wasm/build.sh` links with `-sFILESYSTEM=0` and no
`-pthread`; that is what keeps it true.

Two things would change this, and both are build changes, not deploy changes:

- compiling with `-pthread` (for a multi-threaded extractor), or
- using `SharedArrayBuffer` to hand pages to a worker without copying.

If either ever happens, the page needs `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp` — **and** `Cross-Origin-Resource-Policy:
same-origin` on `/wasm/*`, or the isolated page will refuse to load its own binary. Do not
add these pre-emptively: `require-corp` breaks every cross-origin subresource, and this site
would gain nothing for the trouble.

## 5. Payments: the one thing that forces a server

Everything above assumes the default build. Payments are the single exception, and the cost
is precisely one thing: **the static export.**

A Stripe webhook must be received somewhere, and a secret key may not be in a browser. So a
server is unavoidable the moment payments are switched on. The boundary is drawn so that it
costs nothing until then:

- the payment endpoints are named `route.pay.ts`, and `page.pay.tsx` for the pages;
- `next.config.mjs` adds `pay.ts` / `pay.tsx` to `pageExtensions` **only** when
  `PUBSHIFT_PAYMENTS=1`;
- with payments off those files are not routes at all — not compiled, not exported, not
  reachable — and `output: 'export'` applies.

Verified, default build:

```
Route (app)
┌ ○ /            ○ /_not-found   ○ /credits   ○ /privacy   ○ /robots.txt   ○ /sitemap.xml
○ (Static) prerendered as static content        →  no /api/*, no /batch, no server
```

Verified, `PUBSHIFT_PAYMENTS=1 npm run build:paid`:

```
├ ƒ /api/checkout            ← server-rendered on demand
├ ƒ /api/stripe/webhook      ←
├ ○ /batch   ○ /batch/thanks
```

That build is a Node application and needs a runtime: Vercel, Cloudflare Workers with
`@opennextjs/cloudflare`, Fly.io, or any box running `next start`. The free converter is
byte-for-byte identical in both builds; only the paid surface appears.

**Gotcha:** switching between the two modes without clearing the build cache fails with
`File '.next/types/app/…/page.ts' not found`. Always:

```bash
rm -rf apps/web/.next && npm run build      # or build:paid
```

Environment variables are documented in `apps/web/.env.example`; the setup checklist is at
the end of `docs/PRICING.md`. **Nothing is configured today, and that is the intended
shipping state** — the free tool is the product.

## 6. After deploying, check these five things

```bash
SITE=https://pubshift.app

# 1. The binary is served as WebAssembly, not as a download
curl -sI "$SITE/wasm/$(ls apps/web/out/wasm)/dist/pubshift.wasm" | grep -i 'content-type\|cache-control'
#    expect: content-type: application/wasm
#            cache-control: public, max-age=31536000, immutable

# 2. The CSP actually arrived (this is the one that is usually missing)
curl -sI "$SITE/" | grep -i content-security-policy

# 3. The licence obligations are reachable
curl -sI "$SITE/licences/MPL-2.0.txt" | head -1
curl -sI "$SITE/licences/THIRD-PARTY-NOTICES.md" | head -1

# 4. No server endpoint exists in the free build
curl -s -o /dev/null -w '%{http_code}\n' "$SITE/api/checkout"   # expect 404

# 5. Convert a real .pub file in a real browser, offline
#    Load the page, turn off the network, drop a file in. It must still work.
#    If it does not, the extractor is being fetched from somewhere it should not be.
```

Check 5 is the one that matters. The entire product claim is that nothing is uploaded, and
the only honest test of it is watching a conversion succeed with the network switched off.

## 7. Licence obligations are part of the deploy

`pubshift.wasm` contains libmspub and librevenge compiled in. Serving it is distribution in
Executable Form, which under MPL-2.0 §3.2(a) requires that the corresponding source be
available **and** that recipients be told how to get it. The deploy therefore carries:

- `/licences/MPL-2.0.txt` and `/licences/THIRD-PARTY-NOTICES.md`, staged by `prepare-assets.mjs`;
- a `/credits` page, linked from the footer of every page, naming libmspub and the Document
  Liberation Project and stating the SHA-256 of the exact binary being served.

One step is **not** automated and must be done by hand before the site is public:

```bash
node tools/licence/sources.mjs offer     # -> dist-source/pubshift-corresponding-source-<date>.tar.gz
```

Upload that archive anywhere durable and set `NEXT_PUBLIC_SOURCE_OFFER_URL` to its URL. Until
that is set, the credits page says the archive is not published yet and offers to send it on
request — honest, but an offer-on-request is weaker than a link, and the link is one upload
away. Re-run it whenever the extractor is rebuilt, so the published source matches the
published binary.

`node tools/licence/sources.mjs verify` fails the build if `third_party/` has drifted from
the pin. Run it in CI: a source offer that points at code you did not compile is not an
offer.
